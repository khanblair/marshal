## 6. Rulings

**How the natural-language `when` becomes a real trigger.** The prompt's open question (section 2: `when` is a sentence, not a cron string, so decide how before building the engine). The ruling: **translate at save time and store both halves.** `schedules.when_text` keeps exactly what the person typed and the screen shows it back; `schedules.cron_expr` holds the 5-field spec `ParseCron` derived, and the cron engine only ever sees that. `ParseCron` understands a deliberately small set — an interval ("Every 15 minutes", "Every 2 hours"), a clock time from `time` or from the `HH:MM` inside `when`, and day-of-week from `days` or from the words "weekday"/"weekend" — and **never errors**: an unrecognised sentence still saves, with a best-effort spec (default hour 09:00, every day). Losing a person's typed sentence because Marshal could not parse it would be worse than running it slightly wrong, and the row's `time`/`days` are the parts the edit form never lets them change after creation, so `when` is the only free text. `ParseCron` returns an error in its signature so a stricter caller can exist later; nothing passes one today.

**The structured connection shape (replacing the mock's single free-text `detail`).** Each connection gets its own save shape rather than one string crammed for all of them. GitHub's is `SaveGitHubRequest`; Trello's is the new `SaveTrelloRequest{APIKey, Token, BoardID, WebhookSecret, CallbackURL}` — the key, the board, and the callback URL in the `integrations` row's `config_json` (none of them a secret), the token and the webhook secret together in one keychain entry under the connection's id. The wire's `Integration.Detail` sentence is still built by the connection's own test's `Summary` check, which is how the screen shows one sentence for every kind. Google Calendar and Gmail will follow the same split (their own `SaveXRequest`, their own config/secrets), which is the point of doing Trello's first.

**Where a Trello delivery's signature comes from, and why the callback URL is stored.** Trello signs a delivery over its raw body **followed by the webhook's callback URL**, so the secret alone cannot check one: the URL is half the input and cannot be guessed from the request. The ruling: the connection stores the callback URL (public, in `config_json`) beside the secret, and `/hooks/trello` reads both from the connection on every delivery, so saving them in Settings takes effect without a restart. A delivery is refused with a sentence naming what is missing when either half is absent, and the save refuses a **half-set pair** (a secret with no URL, or a URL with no secret) rather than storing something that could only refuse every delivery later.

**One Marshal project links to one Trello board, and the link is stored rather than inferred.** `SaveTrelloRequest` carries `ProjectID` and `NewCardListID`; the config stores both beside the board, and `SaveTrello` refuses a board with no project. The product scope already rules the one-project-one-board half (section 19.2); what this run had to decide is that the pair is an explicit setting and never a guess - a board whose name resembles a project is still not linked to it, because a wrong link would import cards into the wrong project silently. `NewCardListID` follows the same rule: an empty value is a read-only connection, which the sync treats as a supported state rather than a misconfiguration, and it never picks a list by name.

**A card and an outside item are linked by id, in the table the architecture doc already names.** Migration 0023 adds `external_links (card_id, kind, external_id)` exactly as `docs/architecture.md` section 10 lists it. It is what makes the sync idempotent, and both constraints are load-bearing: the primary key on (card_id, kind) says a card has at most one item per provider, and a **unique** index on (kind, external_id) says an item belongs to exactly one card. The second is the one that stops Trello's own redelivery - which Trello does send - from importing a second card, and it is proven twice: at the schema level in `internal/store` and through a replay in `internal/integrations`. Nothing keys off a title or a description, so renaming either side cannot break the link.

**Dispatch falls back from `Action` to `Kind`.** A schedule's `Action` is a person's free-text sentence describing what happens, never a stable key. `executeSchedule` tries `handlers[Action]` first (for a future structured job action), then `handlers[Kind]` - which is how every brief dispatches today, registered once as `"brief"`.

**`CardStateReview` stands in for "PRs waiting for review" (B8.5).** `internal/briefs` has no `pullrequest`/`review` service dependency; a card in Marshal's own `review` board state is read as the proxy, since a card only reaches that state once its PR is open and waiting.

**`repeats()` gates cron registration and missed-run catch-up to `Cron` and `Interval`.** `ParseCron` always answers a spec regardless of `Trigger`, so without this gate a `One-time` job would fire daily forever and an `Event` trigger would fire on a timer. See §7 for what this leaves undone.

**Product-scope 17.4's "loops with hard limits" are not a Phase 8 build item.** They are `internal/harness`'s existing `Limits`/`StuckDetector` (rounds, time, cost, no-progress stop), built in Phase 5/B5.3 (`internal/harness/limits_test.go`, `stuck_test.go`). B8.1's scheduler triggers a loop by sending a message into a session; the loop's own limits are the harness's, unchanged here.

**`GET /v1/calendar` reads due cards and events through `projects.Service` and `integrations.Service`**, never a query of its own - the same rule B8.5's briefs follow, so a card or a connection is read exactly the way its own route reads it.

**One Google connection per API, matching the mock's own two rows (`gcal`, `gmail`), not one combined "Google" connection.** `apps/web/src/mock/seed/settings.ts` already lists them separately with independent status, and S29d/S29e are separate cutover sections. Only `gcal` is built this run (§7); `gmail` will read `gcal`'s stored OAuth client when it is built, so consent is asked once even though the rows are two.

**The route is `/hooks/trello`, a sibling of `/hooks/github`, not `/hooks/{provider}`.** The prompt's section 4 says to build `POST /hooks/{provider}` so later phases add a provider case. The ruling taken here is narrower on purpose: the two deliveries do not share a verifier (GitHub is HMAC-SHA256 over the body with a `sha256=` header and needs an event header to route; Trello is HMAC-SHA1 over body+callbackURL and has no event header), so a `{provider}` route would be a dispatcher over per-provider verifiers — which is what the two sibling registrations already are, plus a path-value lookup. Adding the calendar/Gmail/Funnel cases is still "one more registration and one more verifier", which is the property the prompt wanted. **If the controller prefers the literal `{provider}` shape, this is the one ruling to revisit**, and it is a small change.
